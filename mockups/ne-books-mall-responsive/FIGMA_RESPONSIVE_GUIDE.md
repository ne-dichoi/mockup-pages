# 피그마 디자이너용 반응형 가이드 — 어디까지 코드가 하고, 어디서 디자인이 결정해야 하나

원본이 피그마 export(PC 1440px)라, 반응형에는 **코드가 자동으로 처리하는 영역**과 **디자이너가 피그마에서 태블릿/모바일 프레임을 직접 그려야 하는 영역**이 나뉜다. 이 문서는 그 경계를 명확히 한다.
기술 규칙은 `RESPONSIVE_GUIDE.md`(개발용)를 참고. 이 문서는 **판단이 필요한 지점**만 다룬다.

---

## 1. 핵심 원칙 — "줄어드는 것"은 코드, "달라지는 것"은 디자인

| 코드(CSS)가 자동으로 하는 것 | 디자이너가 결정해야 하는 것 |
|---|---|
| 폭을 유동적으로 줄이기(px→%) | 좁아졌을 때 **무엇을 숨길지** |
| 2단 → 1단으로 접기 | 접은 뒤 **어느 쪽이 위로 갈지**(정보 우선순위) |
| 카드 4열 → 2열 → 1열 | 카드 안 요소를 **재배열할지, 생략할지** |
| 텍스트 자동 줄바꿈 | 긴 제목을 **말줄임(…)할지 2줄 허용할지** |
| 이미지 비율 유지 축소 | 이미지를 **다른 컷/크롭으로 바꿀지** |
| 절대배치 요소를 흐름으로 되돌리기 | GNB(가로 메뉴)를 **햄버거로 바꿀지, 어떻게** |
| 간격을 토큰 값으로 줄이기 | 터치 타깃을 **얼마나 키우고 재배치할지** |

> 한 줄 요약: **"작아지기만 하면 되는 것 = 코드. 형태·내용·우선순위가 바뀌어야 하는 것 = 디자인."**

---

## 2. 코드가 자동 대응하는 것 (디자이너가 프레임을 안 그려도 됨)

이런 건 PC 프레임 하나만 있어도 코드가 처리한다. 태블릿/모바일 프레임을 따로 안 그려도 무방:

- **콘텐츠 폭 유동화**: 1440 → 화면폭. 컨테이너는 자동으로 줄어든다.
- **단순 세로 나열 섹션**: 배너·공지·푸터처럼 위→아래로 쌓이는 구조.
- **2단 본문 → 1단 접기**: 사이드바+본문, 상품+구매요약 같은 좌우 2단은 자동으로 위아래로 접힌다.
- **N열 카드 그리드 축소**: 4열 → 2열 → 1열 자동.
- **폼 필드 1열 정렬**: 가로 나열 입력칸이 세로로 자동 정렬.
- **이미지 축소**: 비율 유지하며 자동 축소.

→ 이 영역은 **PC 프레임 + 아래 3의 breakpoint별 "결정 항목"만 명세**해 주면 개발이 처리한다.

---

## 3. 디자이너가 피그마에서 그려야 하는 것 (프레임 필수)

아래는 코드가 임의로 결정하면 안 되는, **디자인 판단이 필요한 항목**이다. 각 breakpoint 프레임에서 결정해야 한다.

### 3-1. 만들 프레임 규격

| 프레임 | 권장 폭 | 대상 |
|---|---|---|
| Mobile | **375px** | 스마트폰 |
| Tablet | **768px** | 태블릿 세로 |
| PC | **1440px** | 기존 원본 |

> 폭은 위 3개면 충분하다. 높이는 콘텐츠에 따라 가변(Auto Layout 권장).

### 3-2. 각 프레임에서 결정할 항목 체크리스트

프레임마다 아래를 명시(주석/레이어명/별도 표 어느 쪽이든):

- [ ] **네비게이션 변형**: 가로 GNB를 유지? 가로 스크롤? **햄버거 메뉴로 변경?** 변경 시 열리는 형태(드로어/전체화면)와 안에 담을 항목.
- [ ] **정보 우선순위**: 1단으로 접힐 때 **무엇이 맨 위로**? (예: 상품 상세에서 이미지 먼저 vs 가격 먼저)
- [ ] **숨김/생략**: 좁은 화면에서 **안 보여줄 요소**(부가 설명, 보조 배지, 장식 이미지, 브레드크럼 등).
- [ ] **접기/펼치기**: 필터·정렬·긴 목록을 **아코디언/바텀시트로 접을지**.
- [ ] **재배열**: 카드 내부 요소(썸네일·제목·가격·버튼)의 **모바일 배치 순서**.
- [ ] **테이블 → 카드 변환**: 표의 **어느 열이 카드 제목이 되고, 어느 열에 라벨을 붙이고, 어느 열을 버릴지**(3-3 참고).
- [ ] **터치 타깃**: 버튼·아이콘·체크박스를 **최소 44×44px**로 키운 크기와 간격.
- [ ] **말줄임 vs 줄바꿈**: 긴 제목/설명의 처리(1줄 …  vs 2줄 허용).

## 3-3. 파일럿에서 실제로 "코드만으론 안 됐던" 사례

파일럿(메인·리스트)과 전 페이지 계측에서 확인된, **디자인 결정이 필수였던 실제 지점**:

### 사례 A — 리스트 상품 카드 (파일럿에서 처리함, 단 배치는 임의 결정)
PC에서는 [커버 | 정보 | 우측 세로 액션열(가격·찜·장바구니·구매)]의 3단. 모바일에서 우측 액션열을 **어디로 보낼지**는 코드가 정할 수 없었다.
→ 파일럿은 "정보 아래 가로 한 줄(찜·할인·가격·버튼)"로 폈지만, 이는 **디자인이 확정해야 할 배치**다. 버튼 3개(학습자료/장바구니/바로구매)를 모바일에서 다 노출할지, 우선 1개만 둘지도 디자인 판단.

### 사례 B — 테이블형 페이지 (미처리, 디자인 결정 대기)
아래 4종은 **여러 열을 가진 표**라 단순 축소가 불가능하다. 모바일에서 각 행을 **세로 카드로 재구성**해야 하는데, 이건 코드가 결정할 수 없다:

| 페이지/영역 | 표 구조(열) | 결정 필요 |
|---|---|---|
| 리뷰 목록(`.rgrid-row`) | 평점·작성자·날짜·내용·도움됨 | 카드에서 무엇을 크게, 무엇을 라벨로 |
| 주문 항목(`.oi-row`) | 이미지·상품명·수량·금액·상태 | 수량/금액을 인라인 라벨로 붙일지 |
| 주문/거래 내역(`.tb-row`) | 4열 표 | 제목열 선정 |
| 신간/개정 표(`.br-tr`) | 5열(코드·구분·날짜 등) | 어느 열을 버릴지 |

> **왜 코드가 못 하나**: 헤더행("평점 | 작성자 | 날짜")이 사라지면 데이터만 남아 의미 불명이 된다. "이 값은 금액이다"라는 라벨을 어디에 붙이고, 어떤 값을 카드 제목으로 승격할지는 **정보 설계 = 디자인 판단**이다.

### 사례 C — 달력 (구조적 제약)
마이페이지 등의 달력(`.dp-days` 7열)은 **1열로 접을 수 없다**(요일 구조 파괴). 셀 크기 축소만 가능 → 모바일에서 달력을 유지할지, 다른 UI(드롭다운 등)로 바꿀지 디자인 결정.

### 사례 D — 헤더/GNB (파일럿에서 임시 처리)
파일럿은 태블릿/모바일에서 검색창을 아랫줄로 내리고 GNB는 가로 스크롤로 뒀다. **햄버거 메뉴 전환 여부는 디자인 미결정** 상태다. 가로 스크롤 GNB를 최종안으로 할지, 햄버거로 바꿀지 결정 필요.

### 사례 E — 터치 타깃 (파일럿이 규칙을 위반 중)
찜/공유 아이콘 버튼(22px), 퀵메뉴 아이콘(30px), 체크박스(16px)는 모바일 최소 44px에 미달. 파일럿에서 **의도적으로 미해결**로 남겼다 — 히트 영역 확대/재배치는 디자인이 크기와 간격을 정해줘야 한다.

## 4. 개발 ↔ 디자인 핸드오프 순서 (권장)

반대로 하면(개발이 먼저 구현 후 디자인 리뷰) 재작업이 크게 발생한다. 아래 순서를 권장:

```
1. [디자인] 대표 페이지 유형별로 Mobile(375)·Tablet(768) 프레임 확정
   └ §3-2 체크리스트 항목을 각 프레임에서 결정
   └ 유형: (a)리스트 (b)상세 (c)테이블/내역 (d)폼 (e)정적문서
2. [개발] 확정된 프레임 기준으로 공통 CSS(헤더·breakpoint·유동화) 먼저 구현
   └ 이것만으로 태블릿 대부분 + 모바일 단순 페이지 해결(파일럿 실증)
3. [디자인] 테이블형·상세형 등 개별 결정이 필요한 페이지의 카드화 안 확정
4. [개발] 페이지별 breakpoint 구현 + 3뷰포트 스크린샷 검증
5. [디자인+개발] 스크린샷 합동 리뷰 → 터치 타깃·정렬·우선순위 최종 조정
```

### 왜 "디자인 먼저"인가

- 코드는 "어떻게 줄일지"는 알지만 "무엇을 남기고 버릴지"는 모른다.
- 파일럿에서 **실측된 사실**: 공통 CSS 헤더 수정 1건으로 태블릿 PASS 페이지가 3→18(21페이지 중)로 전환됐다. 즉 디자인이 프레임만 확정해 주면 개발의 공통 작업은 빠르다.
- 반면 **정보 우선순위·숨김·테이블 카드화**를 개발이 임의로 정하면, 디자인 리뷰에서 대부분 반려되어 2~3배 재작업이 된다.

### 유형별 프레임 우선순위(대표 1개씩만 그리면 나머지는 재사용)

| 유형 | 대표 페이지 | 재사용 페이지 |
|---|---|---|
| 리스트 | 리스트_교재구매 | 리스트_학습자료 |
| 상세 | 교재상세 | oxford, 세미나/이벤트 상세 |
| 테이블/내역 | 주문상세 | 마이페이지, 장바구니, 주문결제 |
| 폼 | 후기작성 | 후기수정, 비회원문의 |
| 정적문서 | 공지사항상세 | 각종 상세 안내 |

→ **유형별 대표 5개 프레임(Mobile+Tablet)만 확정**하면, 개발이 나머지 페이지에 패턴을 재사용할 수 있다. 21페이지를 전부 그릴 필요 없다.

## 미해결 · 디자이너 결정 필요 항목 (2차 재작업 시점)

### 이번 스코프에서 완료(index · 리스트_교재구매)
- 공통 헤더 **모바일 전체메뉴 드로어**(햄버거) 구현·검증 완료 — layout.js 기반 20개 페이지에 공통 적용.
- index / 리스트_교재구매 유동화·잘림 해소 완료(3뷰포트 실측 통과).

### 디자이너 결정이 필요한 미적용 항목
1. **GNB 1depth 링크 목적지 미정**: 헤더 GNB의 1depth(초/중등·고등·교과서/자습서·수험/일반·수학/국어·학습자료실·도서몰)가 전부 `href="#"` 플레이스홀더. 드로어는 임시로 하위 항목을 `리스트_교재구매.html`로 연결했다. **각 카테고리의 실제 랜딩 URL을 확정** 필요.
2. **드로어 정보구조(IA)**: 현재 8개 카테고리 + 하위 태그를 1뎁스로 펼쳐 노출. 카테고리별 아코디언 접기/펼치기, 노출할 하위 항목 수, 브랜드(Oxford 등) 배치 등은 **디자인 프레임 확정 필요**.
3. **나머지 19개 페이지 유동화 미적용**(이번 스코프 제외): 교재상세·마이페이지·주문결제/상세·장바구니·고객센터·oxford·각종 상세/폼 등. 특히 **교재상세**(2단→1단 스택, '선택 장바구니 담기' 모바일 가시), **테이블형**(주문/후기/장바구니 카드화), **oxford.html**(269KB 별도)은 정보 우선순위·숨김/재배열 프레임이 있어야 개발 착수 가능.
4. **메인_1.html(대체 메인 목업)**: layout.js를 쓰지 않는 **독립 인라인 헤더** 구조라 공통 드로어가 적용되지 않는다. 이 목업을 계속 유지할지(유지 시 별도 햄버거 구현 필요) 또는 폐기할지 **결정 필요**.
